# Atlas 成熟路线图：从 8 周 MVP 到生产落地

> 直接回答：**不是。**
> [Lean Atlas v1](./lean-atlas-v1.md) 是 **8 周可用的 MVP**，不是“项目完全成熟落地”的终局方案。
> 完全成熟需要 **6–9 个月、四个阶段、多次 Go/No-Go**，并且“成熟”本身是持续运营出来的，不是一次性交付的。
> 本文给出从 MVP 到团队可用、生产可托管、持续演进的完整路线。

---

## 0. 先厘清：三个不同的问题

| 问题 | 对应方案 | 周期 |
|---|---|---|
| **能不能用？** | Lean Atlas v1（单仓库/单用户/本地） | 8 周 |
| **团队能不能日常用？** | Team-ready（多仓库/CI/共享知识/权限） | 16 周 |
| **能不能作为生产服务托管？** | Production/Enterprise（多租户/SSO/SLO/合规） | 24–28 周 |
| **能不能持续变聪明、形成生态？** | Maturity（自我演进/组织知识/市场） | 7 个月起，持续 |

“完全成熟落地”至少包含：

- 产品可用、可安装、可升级、有文档与支持；
- 工程可靠、可观测、可回滚、有 SLO；
- 安全合规、租户隔离、审计、数据治理；
- 多仓库/多服务/团队协作；
- 知识/经验闭环可度量，不是“学习剧场”；
- 成本可预测、ROI 可计算；
- 有生态（VSCode、MCP、Skills、CI/IM 集成）。

---

## 1. “成熟”的八个维度

| 维度 | 成熟标志 | 不成熟的典型表现 |
|---|---|---|
| **产品** | 主路径 ≤ 3 步；安装 ≤ 5 分钟；有升级/回滚 | 功能很多，用户不知道从哪开始 |
| **工程** | CI/CD、测试、Canary、回滚、SLO | 靠开发者本机跑通 |
| **规模** | 多租户、并发、配额、HA/DR | 单机、重启丢状态 |
| **安全** | 威胁模型、沙箱、RBAC、审计、渗透测试 | “先跑起来再说” |
| **知识** | 覆盖/新鲜度/命中率/复发率可度量 | 存了很多，没人用 |
| **生态** | VSCode/CLI/CI/GitHub/Slack/MCP | 只能在终端里用 |
| **经济** | 单任务成本可预测、预算/配额 | 月底账单爆炸 |
| **组织** | 角色、on-call、培训、反馈闭环 | 只有作者会用 |

**成熟不是“功能全”，而是“在真实团队里稳定产生价值”。**

---

## 2. 四阶段总览

| 阶段 | 时间 | 目标用户 | 核心能力 | 退出标准 |
|---|---|---|---|---|
| **S1 MVP** | 第 1–8 周 | 1 个开发者/1 个仓库 | 单仓库、本地、12 工具、Plan/Test、知识库、4+1 UI | 5 个真实任务；恢复；知识可写/可删 |
| **S2 Team-ready** | 第 9–16 周 | 3 个团队/20 开发者 | 多仓库/合同、CI/PR、共享知识、Review、Docker | 3 团队试用；30 任务；安全评审 |
| **S3 Production** | 第 17–28 周 | 企业/多租户 | 服务端、SSO/RBAC、SLO、审计、HA/DR | 99.5% SLO；负载；合规 |
| **S4 Maturity** | 第 7 个月起 | 组织/生态 | 自我演进、组织知识、市场、多 Agent | 复发率降 50%；成本可预测；生态 |

**注意**：S2 不是“把 S1 放大”，S3 也不是“把 S2 部署到云”。每个阶段都有**架构变化**和**新的失败模式**。

> 此前完整方案里的“20–24 周到 GA”是**乐观估计**；把生产化必须做的安全、合规、HA/DR、支持、审计算进去后，S3 生产可用大约在第 28 周，S4 持续演进从第 7 个月开始。

## 3. S1：MVP（第 1–8 周）

### 3.1 目标

单仓库、单用户、本地优先，验证“计划 → 红-绿 → 证据 → 草案 PR”的闭环。

### 3.2 范围

- 6 个必选服务、8 中间件、12 工具、15 表、2+1 配置、4+1 UI；
- SQLite + 本地文件系统 + 可选 Docker；
- 单语言（Python 或 TS）+ 单仓库；
- 知识库：事实/偏好/经验/文档/命令，FTS5 检索；
- Curator：空闲整理、经验验证、周报；
- 10 个 golden tasks。

### 3.3 退出标准（G1）

- 5 个真实任务端到端通过；
- `kill -9` 恢复 100%；
- 知识写入/检索/删除/过期可用；
- 经验候选 → 验证 → 召回链路可用；
- 单任务成本 ≤ $2；
- 无 P0 安全事件；
- 新工程师 1 天跑通主路径。

### 3.4 S1 不应该做的事

- 不做多租户；
- 不做多仓库；
- 不做自我演进；
- 不做 GraphRAG；
- 不做完整知识浏览器；
- 不做团队权限/SSO。

**S1 的唯一目标：证明“这个 Agent 在真实仓库里有用”。**

---

## 4. S2：Team-ready（第 9–16 周）

### 4.1 目标

让 3 个团队、20 个开发者**每天**用它做真实任务，而不是 demo。

### 4.2 新增能力

| 能力 | 内容 | 为什么现在做 |
|---|---|---|
| **多仓库/多服务** | `workspace.yaml`、服务图、合同、变更集、跨仓库 PR | 单仓库客户很快会遇到前后端/多服务 |
| **CI/PR 集成** | GitHub App/GitLab、draft PR、check run、review comment、分支保护 | Agent 必须进入现有工作流，而不是让人来复制 diff |
| **共享知识** | Git-backed 项目知识 + 可选 Postgres 同步；组织知识只读 | 团队需要共享“项目怎么工作” |
| **Review 收件箱** | 候选经验/提案的批准/拒绝/编辑；知识冲突处理 | 学习必须有人把关 |
| **Docker 沙箱** | 每会话容器、网络/资源限制、快照 | 多人/不可信仓库需要隔离 |
| **权限/策略** | 项目级 allow/deny、成员角色、审批 | 团队不能人人 Bypass |
| **评测** | 30–50 任务/仓库；pass^3；成本基线 | 没有评测，无法判断是否变好 |
| **知识质量** | 新鲜度、冲突、过期、删除、来源 | 知识库会开始变脏 |

### 4.3 架构变化

```
本地 daemon（每人）
  ├─ SQLite（本地会话/检查点）
  ├─ Git-backed 项目知识（共享、可 review）
  ├─ Docker 沙箱
  └─ GitHub/GitLab 集成
```

- 仍然**不需要**多租户服务端；
- 共享知识优先用 Git（可 review、可回滚），而不是先上数据库；
- 需要同步时，用轻量 Postgres 只存共享知识/索引，不存会话；
- 每个开发者仍有本地会话/检查点，隐私最好。

### 4.4 退出标准（G2）

- 3 个团队、20 开发者试用 4 周；
- 30 个真实任务，pass^3 ≥ 50%；
- 多仓库变更端到端 1 次通过率 ≥ 60%；
- PR 集成：草案 PR 自动创建、CI 状态回写；
- 共享知识：可 review、可回滚、冲突可处理；
- 安全评审通过（沙箱、密钥、注入、权限）；
- 单任务成本 ≤ $3（简单）/ $10（复杂）；
- 开发者 NPS ≥ 30。

### 4.5 S2 不应该做的事

- 不做多租户 SaaS；
- 不做 SSO/RBAC 全量；
- 不做自我改代码；
- 不做组织级知识图谱；
- 不做 marketplace。

---

## 5. S3：Production/Enterprise（第 17–28 周）

### 5.1 目标

把 Atlas 作为**团队/企业服务**托管：多租户、可审计、可扩容、可运维。

### 5.2 新增能力

| 能力 | 内容 |
|---|---|
| **服务端** | FastAPI + AgentScope Agent Service（`create_app`）、SSE、会话流、workspace manager |
| **存储** | Postgres（会话/知识/审计）、Redis（锁/队列/事件）、S3/MinIO（artifact/快照） |
| **沙箱** | Docker/K8s/E2B，按用户/会话隔离，快照/回收 |
| **身份** | OIDC/SSO、SCIM（可选）、RBAC、租户隔离 |
| **配额** | 按用户/团队/租户的 token/费用/并发配额 |
| **审计** | 工具调用、审批、知识变更、登录、导出 |
| **可观测** | OTel trace、指标、日志、成本、SLO、告警 |
| **可靠性** | HA、备份/恢复、DR、限流、重试、幂等 |
| **合规** | 数据保留/删除、加密、数据驻留、DPA、审计导出 |
| **集成** | GitHub/GitLab、Slack/Feishu/DingTalk、Jira/Linear（MCP） |
| **生态** | MCP Hub/Skill Hub、插件、VSCode Marketplace/Open VSX |
| **评测** | 100+ 任务、红队、负载测试、安全渗透 |

### 5.3 架构变化

```
VSCode/CLI/Web/IM
      │
API Gateway（OIDC/RBAC/配额）
      │
Atlas Server（AgentScope Agent Service）
  ├─ ChatService / SessionService
  ├─ WorkspaceManager（per user/session）
  ├─ KnowledgeService（Postgres + object store）
  ├─ ExecutionService（Docker/K8s/E2B）
  └─ EventBus（Redis/SSE）
      │
Postgres · Redis · S3 · OTel
```

- 从“本地 daemon”变成“本地 + 服务端”双形态；
- 本地仍可用，服务端用于团队/无人值守/IM 触发；
- 会话状态、知识、审计按租户隔离；
- 多副本、滚动升级、跨节点恢复。

### 5.4 退出标准（G3）

- 99.5%/月可用性；
- 100 并发会话/租户压测通过；
- SSO/RBAC/审计/配额可用；
- 备份恢复演练通过（RPO ≤ 15min，RTO ≤ 1h）；
- 安全渗透无 P0/P1；
- 单任务成本可预测（P95 ≤ $10）；
- 3 个企业客户/30+ 开发者日常使用；
- 支持/on-call/runbook 就绪。

### 5.5 S3 不应该做的事

- 不做无边界自我演进；
- 不做跨租户知识共享（除非显式）；
- 不做“全自动合并”；
- 不做模型权重训练；
- 不做无审计的 Bypass。

---

## 6. S4：Maturity/Evolution（第 7 个月起）

### 6.1 目标

从“可靠的 Coding Agent”变成“越用越聪明的工程系统”，并形成生态。

### 6.2 新增能力

| 能力 | 内容 | 前提 |
|---|---|---|
| **自我演进 L3–L6** | 技能/规则/提示词/工具/核心代码提案；沙箱+评测+人审+灰度 | S3 稳定、评测可信 |
| **组织知识** | 跨项目模式、服务目录、事故库、最佳实践 | 多团队数据、隐私审批 |
| **高级检索** | GraphRAG、代码图、跨仓符号 | FTS/向量不够用 |
| **多 Agent 团队** | TeamPipeline/A2A、专业子 Agent | 单 Agent 稳定 |
| **Marketplace** | MCP/Skill/模板市场、认证 | 有留存与生态需求 |
| **成本优化** | 模型路由、缓存、批处理、预算 | 有成本压力 |
| **持续学习** | 复发率、经验质量、课程学习、红队 | 有度量闭环 |

### 6.3 成熟指标（G4）

| 指标 | 目标 |
|---|---|
| 任务成功率 | ≥ 70% |
| 重复错误率 | 较 S3 下降 ≥ 50% |
| 人工接受率 | ≥ 70% |
| 单任务成本 | 简单 ≤ $2，复杂 ≤ $10，可预测 |
| 可用性 | ≥ 99.5% |
| 变更失败率 | < 5% |
| MTTR | < 30 分钟 |
| 周活跃开发者 | ≥ 50 |
| NPS | ≥ 40 |
| 安全 | 无 P0；年度渗透/红队 |

**S4 没有“完成”的一天**：它是持续运营、季度复盘、年度架构评审。

## 8. 团队与预算

| 阶段 | 团队 | 关键角色 |
|---|---|---|
| S1 MVP | 3–5 人 | 架构/后端 2、VSCode/全栈 1、AI/评测 0.5–1、QA 0.5 |
| S2 Team | 5–7 人 | +代码智能/合同 1、知识/Curator 1、DevOps 0.5–1 |
| S3 Production | 8–10 人 | +SRE 1、安全 1、集成 1、支持 0.5 |
| S4 Maturity | 10+ 人 | +研究/演进 1–2、生态/DevRel 1、数据/知识 1 |

**周期**：

- S1：8 周；
- S2：+8 周（第 16 周）；
- S3：+12 周（第 28 周）；
- S4：第 7 个月起，持续 3–6 个月形成稳定能力。

**预算类别**：

- 工程人力；
- 模型 token/推理；
- 沙箱/存储/网络；
- 安全/合规/渗透；
- 支持/生态。

**不要用“加人”解决架构问题**：S2 前先把知识/组件合并做完，否则人越多越乱。

## 10. 每个阶段“不要做”的清单

| 阶段 | 不要做 | 原因 |
|---|---|---|
| S1 | 多租户、SSO、GraphRAG、自我演进 | 还没验证核心价值 |
| S2 | 自建 SaaS、全量 RBAC、市场 | 团队版先用 Git/本地验证 |
| S3 | 无边界自修改、全自动合并 | 安全/合规不允许 |
| S4 | 为了“酷”而上新技术 | 必须以真实问题为前提 |

**通用规则**：没有真实用户案例，不做。

## 11. Go / No-Go 门槛

### G1（第 8 周）

- 5 个真实任务；
- 恢复 100%；
- 知识可写/可删；
- 成本 ≤ $2；
- 无 P0。

**不达标**：回到 S1，不要进入 S2。

### G2（第 16 周）

- 3 团队/20 开发者；
- 30 任务/pass^3 ≥ 50%；
- 多仓库变更；
- CI/PR 集成；
- 安全评审；
- NPS ≥ 30。

**不达标**：不要上服务端；先修产品/知识质量。

### G3（第 28 周）

- 99.5% SLO；
- 100 并发；
- SSO/RBAC/审计；
- DR 演练；
- 渗透无 P0/P1；
- 3 企业客户。

**不达标**：不要扩销售；先修可靠性/安全。

### G4（第 7 个月起）

- 任务成功率 ≥ 70%；
- 复发率降 50%；
- 成本可预测；
- 50 周活；
- NPS ≥ 40。

**不达标**：不要做市场/生态；先修学习闭环。

## 12. 30 天行动建议

### 第 1–2 周

- 按 `lean-atlas-v1.md` 的 W1/W2 开工；
- 选定 1 个真实仓库、1 个开发者；
- 记录基线：任务成功率、时间、成本、人工纠正次数。

### 第 3–4 周

- 完成 Plan/Test/Knowledge；
- 跑 5 个真实任务；
- 第一份“重复错误”报告。

### 第 2 个月

- 10 个 golden tasks；
- Curator 夜间运行；
- 决策：是否进入 S2。

### 第 3 个月

- 若 G1 达标：启动 S2（多仓库/CI/共享知识）；
- 若未达标：回到 S1，不要加功能。

---

## 13. 结论

**Lean Atlas v1 是“能用”，本文是“成熟”。**

- 8 周：证明有用；
- 16 周：团队日常可用；
- 28 周：生产可托管；
- 7 个月起：持续变聪明、形成生态。

“完全成熟”不是一份 8 周计划能交付的；它是 **MVP → 团队验证 → 生产化 → 持续演进** 的分阶段工程。每一阶段都要有真实用户、真实任务、真实指标，否则“成熟”只是文档里的形容词。
